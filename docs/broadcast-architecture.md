## 1. Repository audit

Findings below are what actually exists in this repo today (file:line references), gathered before any of Phase 1 was written, per the "inspect, don't assume" rule this feature is being built under.

### 1.1 Stack
- Next.js `^16.1.6`, App Router, React 19, TypeScript. Next 16 renamed `middleware.ts` → `src/proxy.ts` — **read `node_modules/next/dist/docs/` before writing route handlers**, this repo's version has real breaking changes from older Next.js training data (see `AGENTS.md`).
- MySQL via `sequelize` `^6.37.7` + `mysql2`. No ORM migration tool (Sequelize CLI, Umzug, etc.) — schema is versioned as hand-written `.sql` files under `migrations/`, applied by `scripts/setup-database.js`.
- `zod` `^4.4.3` is already a dependency (not yet used for env validation, but available for the API-layer validation Phase 3+ will need).
- Auth: custom JWT (`jsonwebtoken` + `jose`), no NextAuth despite `docker-compose.prod.yml` referencing it (stale boilerplate — see [1.7](#17-deployment)).
- At audit time (before this feature), no Redis/BullMQ dependency existed and background jobs ran via `node-cron` in-process. **Redis + BullMQ were added for this feature** - see [2. Runtime decision](#2-runtime-decision-redis--bullmq-superseding-the-earlier-db-poll-recommendation).

### 1.2 Auth / session
- `src/lib/auth.ts` — `verifyToken()` verifies an HS256 JWT, rejects any token carrying an MFA-pending `purpose` claim.
- `src/lib/apiAuth.ts` — `requireAuth(request, permissions?)` is the standard route-handler guard: reads the `auth-token` cookie or `Authorization: Bearer`, returns either a `User` or a ready-to-return 401/403 `NextResponse`. Companion `isAuthError()` type guard.
- Usage pattern (`src/app/api/lead-remarks/route.ts:16-18`):
  ```ts
  const auth = requireAuth(request, ['leads.update']);
  if (isAuthError(auth)) return auth;
  ```
- Separate parallel sessions exist for the client portal (`clientAuth.ts`) and the mobile app (`mobileAuth.ts`) — irrelevant to this feature, which is staff-only.

### 1.3 Tenant / branch / role boundaries
- **No literal "tenant" or "project" concept.** The scoping unit is **branch** (`CrmBranch`, table `crm_branch`), plus region. This is why every new table in this feature uses `branch_id` (nullable = company-wide), not `tenant_id`/`project_id`.
- **No `hasPermission(user, key)` helper exists.** Permission checks are inline: `requireAuth(request, ['some.permission'])` at the route level, and role-name substring matching (`src/lib/roleChecks.ts`: `isCeo`, `isBranchManagerOrCeo`, etc.) for finer-grained branch-write scoping (`src/lib/branchScopeGuard.ts`).
- RBAC data model: `crm_role` → `crm_role_permissions` → `crm_permissions` (`permission_key`, `module`, `action`), seeded/upserted by `scripts/seed-roles-permissions.js`. Two permission keys relevant to this feature **already exist** in `adminPermissions` (`scripts/seed-roles-permissions.js:87-88`): `campaigns.manage`, `templates.manage`. Phase 3+ will extend this list (`campaigns.launch`, `campaigns.export`, `workflows.manage`, `workflows.publish`, `bots.manage`, …) — **not done in Phase 1**, since no route exists yet to gate.
- `CrmTeams` exists as a model but `CrmEmployee` has no `team_id` column — it's effectively dead. Don't build on it.
- `src/lib/apiCrud.ts`'s `listScope(auth)` hook is the closest thing to a reusable branch-scoping primith — Phase 3 API routes should use the `createCrudHandlers`/`apiCrud.ts` pattern where the entity is simple CRUD (e.g. segments, templates), and hand-written route handlers (matching `src/app/api/branches/route.ts`) where it isn't (campaign launch, workflow publish/simulate).

### 1.4 Lead / contact / pipeline core models
- **`CrmcForumLeads`** (table `crm_forum_leads`) is the actual core lead/contact record — **not** `CrmClients` (client-portal account, created only after conversion) or `CrmProspects` (a narrower, separate entity). Every "contact" reference in this feature's schema is `lead_id → crm_forum_leads.id`.
- Key columns used by this feature: `branch`, `region`, `assignTo` (assigned employee), `email`, `mobile`, `whatsapp_number` (added by `migrations/20260724_lead_whatsapp_number.sql` — distinct from `mobile`).
- **`CrmcOpportunities`** (table `crm_opportunities`) is the deal/pipeline model, with free-text `status`/`stage` columns (no separate stage lookup table). Not directly referenced by Phase 1 schema, but campaigns/workflows will likely want an `opportunity.stage_changed` trigger in Phase 4 — noted for later, not built now.

### 1.5 Background jobs — no existing queue infrastructure to reuse as-is
- `node-cron` schedulers are registered once at server boot from `src/instrumentation.ts` (Next 16's `register()` hook), each in its own `*-cron.ts` file.
- `src/lib/jobQueue.ts` is a **minimal DB-backed async job queue** (still used by unrelated existing CRM features, e.g. queued transactional emails - untouched by this work), explicitly documented in its own header comment as "deliberately not Redis/BullMQ." That reasoning no longer applies to the broadcast/workflow feature specifically - see [2. Runtime decision](#2-runtime-decision-redis--bullmq-superseding-the-earlier-db-poll-recommendation).
- A parallel Vercel Cron path (`/api/cron/*` routes + `CRON_SECRET`) exists for at least the Meta-leads jobs (`docs/META_LEADS_INTEGRATION.md`), for the same reason node-cron alone can't be trusted on serverless.

### 1.6 Webhooks
- One precedent: `src/app/api/webhooks/meta/route.ts`. Pattern to replicate for provider (WhatsApp/email/SMS) webhooks in Phase 3: read raw body via `request.text()` before parsing (HMAC needs the raw bytes), verify signature (`src/lib/meta/webhook.ts`'s `crypto.timingSafeEqual` pattern), `INSERT IGNORE` a raw event row keyed by a content hash for dedup, return `200` immediately, process async.

### 1.7 Migration tooling
- `scripts/setup-database.js` applies every `migrations/*.sql` file in **plain alphabetical order** (`fs.readdirSync(...).sort()`, non-recursive) — the `YYYYMMDD_` filename prefix is what makes that chronological. **No migrations-tracking ledger** — idempotency comes from `CREATE TABLE IF NOT EXISTS` / known duplicate-object MySQL error codes being swallowed, not from a "have I run this" table.
- **No `up`/`down` support at all** in the existing tooling. This feature adds its own convention for that: a `migrations/rollback/` subdirectory (invisible to the non-recursive glob above, confirmed by reading `scripts/setup-database.js:767`), holding a hand-written `.down.sql` per forward migration.

### 1.8 Environment / encryption
- No central zod-validated env module. Env vars are read ad hoc via `process.env.X`.
- `src/lib/encryption.ts` already provides AES-256-GCM `encryptSecret()`/`decryptSecret()`, keyed from `DATA_ENCRYPTION_KEY`/`ENCRYPTION_KEY`/`JWT_SECRET` (in that fallback order). **Reused as-is** for `crm_messaging_integrations.credential_ref` — no new encryption code needed.

### 1.9 Deployment
- Vercel is the documented/actual deployment target (`README.md`) for the Next.js app itself. `Dockerfile.prod` + `docker-compose.prod.yml` exist as an alternative persistent-Node-process path; the Postgres/NextAuth bits in that compose file don't match this app's real MySQL/Sequelize/custom-JWT stack (stale generic boilerplate), but its `redis` service is **now genuinely used** - see [the runtime decision below](#2-runtime-decision-redis--bullmq-superseding-the-earlier-db-poll-recommendation). `src/instrumentation.ts`'s node-cron schedulers only run meaningfully in a long-lived process, which Vercel serverless functions are not - the direct reason the broadcast/workflow worker runs as its own standalone process (`workers/index.ts`, `npm run worker`) rather than inside Next.js at all.

### 1.10 Tests
- Vitest (`tests/unit/**/*.test.ts`) is pure-logic only, **no DB, no mocking** — confirmed by running the new `tests/unit/broadcastDedupeKeys.test.ts` and `tests/unit/broadcastModels.test.ts` added in this phase (9/9 passing, full-repo `tsc --noEmit` clean).

### 1.11 UI design system
- `src/components/ui/` — hand-rolled components (`button.tsx`, `card.tsx`, `data-table.tsx`, `drawer.tsx`, `select.tsx`, …), no shadcn/ui or `cva`. Tailwind v4, CSS-variable tokens in `src/app/globals.css` (`--dmc-*`/`--cmg-*`), no `tailwind.config.js`. No existing `dialog.tsx`/`modal.tsx` in `ui/` — Phase 7 UI work will need to either find one elsewhere or add one.

### 1.12 Existing messaging code — reused, not replaced

- **WhatsApp**: `src/lib/whatsapp.ts` — `sendWhatsAppMessage()` via Meta WhatsApp Cloud API (`fetch`), logged to `crm_whatsapp_delivery_log`. - `CrmCampaigns` (table `crm_campaigns`: `id, campaign, created, created_by, status`) and `CrmEmailTemplates` (table `crm_email_templates`: `id, program, template, created, status, ops, sales, created_by`) are **legacy, unrelated** tables — a simple "name a marketing campaign" tag and a plain-text email-body picker, with no versioning, no channel concept, no recipient tracking. ## 2. Runtime decision: Redis + BullMQ (superseding the earlier DB-poll recommendation)

**Status: resolved, implemented.** This section originally recommended extending the existing `crm_job_queue`/node-cron pattern instead of adopting Redis/BullMQ, to avoid new infrastructure. The user explicitly overrode that recommendation and asked for the originally-specified Redis + BullMQ stack to be actually installed and wired in - not the DB-poll substitute. That is what Phase 3/4's runtime now uses.

- **Redis**: confirmed already installed and running locally (Windows service, `redis-server.exe`) - reachable at `redis://localhost:6379` (`redis-cli ping` → `PONG`). `docker-compose.prod.yml` already declares a `redis` service for production, previously unused - this is now its first real consumer.
- **Packages added**: `bullmq`, `ioredis`, and `tsx` (to run the standalone TypeScript worker process without a separate build step - see below).
- **`src/lib/redis.ts`**: shared `ioredis` connection (`REDIS_URL`, default `redis://localhost:6379`), `maxRetriesPerRequest: null` per BullMQ's own documented requirement.
- **`src/lib/queues/broadcastQueue.ts`** / **`src/lib/queues/workflowQueue.ts`**: BullMQ `Queue` definitions. A broadcast recipient is enqueued (`jobId: recipient-<id>` for natural BullMQ-level dedup) the instant it's ready to send; a workflow step is enqueued the instant it's created; a wait is scheduled as a BullMQ **delayed job** firing at its exact deadline (replacing "discovered within the next minute" with deadline-accurate resolution).
- **`workers/index.ts`** (new, project root - NOT part of the Next.js app): the actual "separate persistent Node.js worker and scheduler process" the spec calls for. Run via `npm run worker` (`tsx workers/index.ts`). Hosts two BullMQ `Worker`s (broadcast recipients, workflow steps/waits) plus a lightweight interval-based scheduler (campaign activation every 30s; a reconciliation sweep every 5 minutes as a safety net for the rare case an enqueue call itself failed - see below). It imports and reuses `processBroadcastRecipient()`/`processWorkflowStepById()`/`resolveWaitById()` from the existing lib files - this is a thin entrypoint, not a second implementation of the send/execute logic.
- **`src/instrumentation.ts`**: the broadcast/workflow cron registrations added in the earlier DB-poll design have been **removed** (along with the now-dead `src/lib/broadcast-worker-cron.ts` / `src/lib/workflow-runtime-cron.ts` files) - per the spec's own "avoid running long-lived workers in route handlers" / "deployed outside Vercel/serverless handlers" rule, this logic does not belong inside the Next.js process at all, not even flag-gated. `processDueBroadcastRecipients()`/`processDueWorkflowSteps()`/`resolveDueWaits()` still exist as reconciliation-sweep functions, but are only ever called from `workers/index.ts` now.
- **Verified end-to-end**, not just typechecked: a standalone smoke test (`Queue.add()` → `Worker` processed it → job completed) confirmed against the real local Redis instance. One finding worth noting: that Redis instance reports version **5.0.14**, below BullMQ's recommended minimum of 6.2.0 - basic enqueue/process worked fine in the smoke test, but some newer BullMQ features may not be fully supported; upgrading Redis is worth doing before relying on this in production.
- **API wiring**: `POST /api/broadcast/campaigns/[id]/launch` enqueues every newly-inserted recipient after its transaction commits (never inside it, so a rollback can never leave an orphaned BullMQ job); `enrollLead()`/`dispatchNextSteps()` in `src/lib/workflowRuntime.ts` do the same for workflow steps.

### Why a DB row is still the source of truth, not the BullMQ job

Every function BullMQ calls (`processBroadcastRecipient`, `processWorkflowStepById`, `resolveWaitById`) re-derives its own eligibility from the database and is safe to call more than once for the same id (an atomic `UPDATE ... WHERE status = 'queued'`-style claim guards each one) - this matters because BullMQ, like any queue, can redeliver a job more than once, and because the reconciliation sweep and a BullMQ job can legitimately target the same row. This was the correctness property the original DB-poll design already had (lease columns, idempotency keys); adopting BullMQ as the trigger mechanism didn't require weakening it.

### Sequelize models
All 20 tables have a matching model under `src/models/` (`CrmMessagingIntegrations.ts` … `CrmAutomationAuditLogs.ts`), following the exact convention of the most recent precedent in this codebase (`src/models/CrmContract.ts`): camelCase TS attributes mapped via `field: 'snake_case'`, `timestamps: false` with explicit `createdAt`/`updatedAt` columns, `freezeTableName: true`, `associate(models)` static methods wiring `belongsTo`/`hasMany`. All registered in `src/models/index.ts` (both the `models` map that drives `associate()` wiring, and the individual named exports other modules import from).

### Design conventions followed
- `branch_id` (nullable) instead of `tenant_id`/`project_id` — see [1.3](#13-tenant--branch--role-boundaries).
- `lead_id → crm_forum_leads.id` for every "contact" reference — see [1.4](#14-lead--contact--pipeline-core-models).
- FK `ON DELETE`: `RESTRICT` for mandatory attribution/links, `SET NULL` for nullable "nice to know" attribution, `CASCADE` only for a strict parent/child pair (recipients under a campaign, step executions under an enrollment, messages under a session) — matching the convention documented in `migrations/20260923_contracts_schema.sql`.
- Soft delete (`is_deleted`/`deleted_at`) on user-owned, deletable records (integrations, segments, templates, campaigns, workflows) — not on append-only/event tables.
- `crm_message_templates.current_draft_version_id`/`current_published_version_id` and `crm_workflow_definitions`' equivalents are **intentionally not FK-constrained** (avoids circular table-creation order between a parent and its own "current version" pointer); enforced at the application layer instead. Documented inline in the migration file.
- Immutability: `crm_message_template_versions.is_published` and `crm_workflow_versions.is_published` are flags the application must never flip back or `UPDATE` a row after — a new version row supersedes it instead. Not DB-enforced (no trigger); Phase 3/4 write paths must respect this.

### Feature flag
- `BROADCAST_AUTOMATION_ENABLED` (`.env.example`), read by `src/lib/broadcastFeatureFlags.ts`'s `isBroadcastAutomationEnabled()`. Nothing calls it yet (no routes exist) — it exists so Phase 3+ has a single kill switch from day one, matching this repo's existing per-feature flags (`META_INTEGRATION_ENABLED`, `RENEWAL_REMINDER_CRON_ENABLED`).

### Security review (self-run, `security-review` skill) and fixes

Run against the full branch diff after the above was built. Two passes were needed - the first pass's own diff-gathering script silently skipped untracked *directories* (`git status --short` reports an untracked dir as one path, not per-file), which meant it missed `src/app/api/broadcast/`, `src/lib/queues/`, and `workers/` entirely - exactly where the highest-severity findings turned out to live. Fixed by re-generating the diff with `find` over those directories and re-running. Five findings confirmed and fixed, all re-validated with `tsc --noEmit` (clean), `eslint` (0 errors), `vitest run` (196/196 passing), and `next build` (green) after the fixes:

1. **SSRF via redirect bypass, `action.webhook`** (`src/lib/workflowRuntime.ts`) - `isWebhookHostAllowed()` only validated the URL configured on the node; a plain `fetch()` would still auto-follow a 3xx response to wherever its `Location` header pointed, bypassing the allowlist if the (allowlisted) target host was compromised or itself proxied elsewhere. Fixed: `redirect: 'manual'`, and any 3xx response is now treated as a failed call rather than followed.
2. **Unescaped HTML injection into outbound campaign/workflow emails** (`src/lib/broadcastTemplateRender.ts`) - `renderTemplateText()` did raw string substitution with no HTML-escaping, and was being used to render a template's `exportHtml` (the actual email body) with lead-controlled `{{name}}` values. A lead whose name field contained markup could inject it into an email sent from the company's own domain to other recipients. Fixed by adding `renderTemplateHtml()` (escapes each substituted value) and switching both real send paths (`src/lib/broadcastWorker.ts`, `src/lib/workflowRuntime.ts`) to it for the HTML body specifically; subject/plain-text still use the unescaped variant since Resend is called via its JSON REST API (`src/lib/mailer.ts`), not raw SMTP headers, so there's no header-injection surface there.
3. **Campaign `segmentId` dereferenced with no ownership check (IDOR)** - a private (non-shared, not-your-branch) segment's audience could be used by anyone holding `campaigns.manage`, bypassing `crm_contact_segments`' own owner/branch/`isShared` model. Fixed by extracting the ownership check `segments/[id]/route.ts` already had into a shared `canAccessSegment()` helper (`src/lib/roleChecks.ts`) and calling it wherever a `segmentId` is dereferenced: campaign create, campaign update, and campaign launch.
4. **Latent cross-branch IDOR on single-ID campaign/template/workflow routes** - every `GET`/`PUT`/`DELETE`/action route keyed by `:id` fetched the record and acted on it with no branch check, unlike their own list (`GET /`) routes, which do scope by branch. Not exploitable today (only CEO/Director of Sales - both `canViewAllBranches()` - hold `campaigns.manage`/`templates.manage`/`workflows.manage`), but latent for whenever a branch-scoped role is granted one of those permissions. Fixed with a new shared `canAccessBranchScopedRecord()` helper (`src/lib/roleChecks.ts`, mirrors the list routes' own `branchId`-or-`null` scoping) applied across all 15 single-ID/action routes under `campaigns/[id]/*`, `templates/[id]/*`, and `workflows/[id]/*`.
5. **Client-controlled `branchId` on create** - `campaigns`, `templates`, `workflows`, and `segments`' `POST` routes all took `body.branchId ?? auth.branch ?? null`, letting any caller assign a new record to an arbitrary branch instead of only their own. Fixed by dropping `body.branchId` and using `auth.branch ?? null` unconditionally on all four.

## 12. Closing three more of the previously-listed gaps: remaining trigger listeners, a second raw-INSERT lead-creation path, and real `assign_agent` round-robin

- **All 6 `trigger.*` node types now have a listener** (`src/lib/workflowTriggers.ts`), not just `trigger.lead_created`/`trigger.inbound_message`:
  - `fireLeadUpdatedTrigger(leadId, changedFields)` and `fireStageChangedTrigger(leadId, fromStage, toStage)` - both called from `src/app/api/leads/[id]/route.ts`'s `PUT` handler, which now tracks which fields *actually changed value* (not just which fields the request included - re-saving an unchanged value doesn't fire either trigger) while it builds its `UPDATE` statement. `trigger.lead_updated`'s optional `watchedFields` filter is honored; `trigger.stage_changed`'s optional `fromStage`/`toStage` filters are honored.
  - `fireFormSubmittedTrigger(leadId, formKey)` - called from both public lead-capture paths, `src/lib/webToLeadsIngest.ts` (`formKey: 'web-to-leads'`, covers the website form, Meta Lead Ads, Salesforce, and Contact Form 7 - everything that goes through `ingestWebToLead()`) and `src/app/api/lead-intake/route.ts` (`formKey: 'lead-intake'`).
  - `fireCampaignEventTrigger({leadId, campaignId, eventType})` - called from every site that already records a `crm_broadcast_events` row for an identifiable lead: `src/lib/broadcastWorker.ts` (`'sent'`), and `src/app/api/webhooks/whatsapp/route.ts`'s status-change handler (`'delivered'`/`'read'`) and reply-detection path (`'replied'`). The node's `configSchema` also allows `'bounced'`/`'opted_out'`, matching the originating spec, but neither has a concrete event source in this codebase yet: WhatsApp reports a delivery failure as `'failed'` (not a distinct bounce), and an opt-out is recorded as a consent-state change, not a per-campaign event - so those two remain un-fireable until something produces a real event for them.
- **Second raw-INSERT lead-creation path found and fixed** - auditing every lead-creation call site (not just the bulk-Excel-import branch already known about) turned up that `src/lib/webToLeadsIngest.ts`'s `ingestWebToLead()` - the function behind the website form, Meta Lead Ads, Salesforce, and Contact Form 7 - has its own `CrmcForumLeads.create()` and never went through `insertLeadRecord()` at all. This is a bigger gap than the bulk-import one: it's a live, continuously-used lead source, not a rare staff action. Rather than rewrite its already-tuned column list onto `buildDefaultLeadData()`/`insertLeadRecord()` (real regression risk to a production intake path, for no behavioral gain), both `fireLeadCreatedTrigger()` and `fireFormSubmittedTrigger()` are now called directly after its `create()` call, same fire-and-forget pattern `insertLeadRecord()` itself uses. The bulk-Excel-import branch (`src/app/api/leads/route.ts`) got the same direct-call treatment for `fireLeadCreatedTrigger()`, closing the gap called out in §9's "not yet built" list.
- **`action.assign_agent`'s `strategy: 'round_robin'` no longer throws `NotImplementedNodeError`** (`src/lib/workflowRuntime.ts`) - it now calls `resolveLeadAssignment()` (`src/lib/assignmentRuleEngine.ts`), the exact same round-robin engine `src/lib/webToLeadsIngest.ts` and `src/app/api/lead-intake/route.ts` already use, so a workflow-driven assignment rotates through the same `crm_lead_round_robin_state` cursor and rule set as every other assignment path rather than a second, workflow-only algorithm. An empty branch roster (`resolveLeadAssignment` throwing "No active employees are available") leaves the lead as-is rather than failing the step, matching every other round-robin caller's own behavior. Both the round-robin and direct-`agentId` paths now go through `recordLeadAssignment()` (previously only the round-robin path was even attempted, and the direct-`agentId` path skipped the audit trail entirely) so a workflow assignment stamps the same `transfer_date`/`transfer_time` fields and logs the same `lead_assigned` remark a manual assignment does.
